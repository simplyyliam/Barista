# Barista

A macOS-style menu bar (and later a dock) for Windows, built with Tauri. It replaces the system
tray: tray icons live in the bar, and apps can add real menu bar items through a public SDK
(`@barista/sdk`, prefix `BA`). The bar reserves screen space like macOS.

## Frontend structure (Liam's, `apps/bar/src/`)

- `widgets/` are parent bodies (bar, menu panel, overflow, settings window). `features/` hold the
  pieces inside them, in a folder with the **same name** as their widget:
  `widgets/barista/barista.tsx` renders the pieces in `features/barista/`.
- A feature folder can have its own `hooks/`, `lib/`, `utils/` when nothing else uses them.
  Shared code lives in `shared/` (bindings, stores, helpers). A feature never edits another feature.

## Hard rules

1. **The bar owns the bar.** Client apps never draw into it. They register a status item and
   either send a menu (the bar draws it) or own a popover window (the bar tells it where to anchor).
2. **The protocol is the product.** Message types live once in Rust (`crates/protocol/`) and are
   generated into `packages/sdk/src/protocol.ts`. Protocol changes are versioned
   (`protocolVersion`), stay backward compatible within a major version, and get a test.
3. **Never trust a client.** Validate every message (sizes, ids, icon data); one bad or slow
   client must never freeze or crash the bar.
4. **Lifecycle is the bar's job.** Heartbeat every client; remove items from dead clients; the SDK
   reconnects and re-registers by itself after a bar restart, and waits if the bar isn't running yet.
5. **Rust holds the logic here** (unlike Blocksy): AppBar reservation, IPC server, item registry,
   tray bridging, window anchoring. The frontend only renders state it gets from bindings.
6. **Public API names are conventional** (see "SDK naming"). No invented words, no Windows jargon
   ("tray", "notify icon", "AppBar") in the public API.
7. **Windows-only APIs sit behind small modules** (`src-tauri/src/platform/windows/`), so the rest
   of the code reads like plain Rust.
8. **Multi-monitor and DPI from day one.** Every position or size is in physical pixels at the
   boundary and converted once.
9. **Performance budget:** the bar idles near 0% CPU and stays small in memory. No polling where
   a Windows event exists. Results go in `docs/perf/`.
10. Architectural decisions get a short ADR in `docs/decisions/`.

## Layout

```text
apps/bar/                 Tauri app
  src/                    React frontend (Liam)
  src/shared/bindings.ts  generated by tauri-specta (never edit)
  src-tauri/              Rust (Claude)
    src/commands/         Tauri commands for the frontend
    src/ipc/              named-pipe server, client sessions, heartbeat
    src/registry/         status items, menus, popover anchors
    src/platform/windows/ AppBar, tray bridging, monitors, DPI
crates/protocol/          message types shared by bar and SDK (source of protocol.ts)
packages/sdk/             @barista/sdk (BA.StatusItem etc.)
  src/protocol.ts         generated from crates/protocol (never edit)
packages/ui/              @barista/ui: shared shadcn/ui (preset base-mira); apps import its styles.css
  src/styles.css          shadcn's generated theme (:root, @theme, dark); leave it as generated
packages/react/           @barista/react (later)
examples/test-client/     tiny app that registers items, used in tests and demos
docs/                     release plan, ADRs (decisions/), design, research, perf
```

Nothing imports from `apps/`. The SDK never imports Tauri.

## SDK naming

- Main style: `import * as BA from '@barista/sdk'` then `BA.StatusItem`, `BA.Menu`, `BA.Popover`.
  Also export prefixed names (`BAStatusItem`, `BAMenu`, ...).
- Names: `StatusBar` (host), `StatusItem`, `Menu`, `MenuItem`, `Popover`; later `Dock`, `DockItem`.
- `create` / `remove` for lifecycle, `set...` for changes (`setLabel`, `setIcon`, `setMenu`,
  `setPopover`), `on('click' | 'open' | 'close')` for events.
- Menus use the Electron-style template (`label`, `type`, `checked`, `accelerator`, `click`,
  `role`, `submenu`).
- Every public function gets a TSDoc comment with a short example.

## Git workflow (PRs)

- `main` is protected by a ruleset: no direct pushes, PRs only.
- Branch from `main`: `feature/<name>`, `fix/<name>`, `chore/<name>`, `docs/<name>`.
- Commit in small steps using Conventional Commits (feat, fix, chore, docs, refactor, test), with a
  short bullet-point body listing what was done. Bodies are bullets, never paragraphs.
- When done, push the branch and open a PR with `gh pr create`: short summary, what Liam needs to
  test, and bench results if perf-related. Small PRs get squash-merged, release PRs a merge commit (Liam decides).
- Never push to `main` or merge PRs yourself.

## Releases

- Two tracks: the bar app (`v0.X.Y`, installer + auto-updater) and the SDK (`sdk-v0.X.Y`, npm).
  They version separately.
- `/release [sdk]` (`.claude/commands/release.md`): checks, version bump and changelog on a
  `release/...` branch, then a PR. After Liam merges, `/release tag [sdk]` tags the merge commit
  (annotated, never pushed).
- `pnpm release` (Liam) pushes the tag; the GitHub Action builds the signed installer and updater
  files into a draft GitHub release Liam publishes. An `sdk-v*` tag publishes the SDK to npm.
- Release reports go in `.private/releases/`; the updater signing key lives in `.private/updater/`
  (created by `pnpm updater:keygen`).

## Commands

- Root: `pnpm dev`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm bench`
- Root: `pnpm gen` (bindings + protocol types), `pnpm test-client`, `pnpm release`, `pnpm updater:keygen`
- Root (one Cargo workspace: the app and `crates/protocol`): `cargo check --workspace`,
  `cargo clippy --workspace --all-targets`, `cargo test --workspace`

## Never

- Never edit `bindings.ts` or `protocol.ts` by hand (run `pnpm gen`).
- Never call Tauri's `invoke` directly; use the generated `commands` (lint enforces).
- Never edit `apps/bar/src/` (Liam's frontend), unless the `/goal` run says `UI: full`.
- Never read, print or commit anything in `.private/` (updater signing key, release reports).
