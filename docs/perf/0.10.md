- 6 processes counted (the bar and its WebView2 children), 12 logical cores.
- CPU: total over 66 s after 10 s of settling, divided by cores. The ticking row is the same with `examples/test-client` running (one label update per second).
- Latency is measured over the pipe with a minimal client: the time from sending the message until `debug.listItems` shows it. The UI sees it about one frame (16 ms) later, because `items-changed` is coalesced; the render time is the UI's.
- Popovers: from the click (sent over the pipe as `debug.click`) until the app receives `popover.show` / `popover.hide`. Window visible and focused is timed with a real mouse click by `scripts/popover-latency.ps1`.
- Menus: the window time is from the click (sent over the pipe as `debug.click`) until Windows reports the menu window visible; React drawing the entries comes on top once the UI exists.
- Machine: AMD Ryzen 5 7430U with Radeon Graphics, 15 GB RAM.

## Notes (v0.10)

- Build: `pnpm --filter @barista/bar exec tauri build` with the new release profile (fat LTO, `opt-level = "s"`, one codegen unit,
  stripped). The installer is 4.1 MB; `barista.exe` is 13.6 MB.
- Private memory went from 131 MB (0.9) to 138 MB, still over the 120 MB budget; with five script items 137 MB (0.9: 109 MB, so the
  two numbers are now almost equal and the "with scripts" one is the noisier of the two). One run each, so treat +-5 MB as noise.
- **The memory pass from `releases/v0.10.md` was not done in this release** (one change at a time, measured with `pnpm bench`). Candidates, in
  the order they are likely to pay off: how many WebView2 renderer processes are really needed, the prebaked panel window while it is
  hidden, icon data URLs held in the registry, and the WebView2 flags (ADR 0033). It moves to v0.10.x.
- The tray row says "not measured" because the fake tray icons did not show up in this run (same as 0.9).
- Installer test on the same build: install 22 s, uninstall 22 to 45 s (see CHECKPOINT "Fix next").

## Where the memory goes (memory pass, measured, no change made)

Idle bar, 20 s after start, fast-profile build of the final source (private bytes per process; Rust optimisation level does not matter here):

| Process | MB |
|---|---|
| `barista.exe` (the Rust side) | 21 |
| WebView2 browser process | 76 |
| WebView2 renderer (one shared, `--renderer-process-limit=1`) | 70 |
| WebView2 utility (network, storage) | 13 + 7 |
| crashpad handler | 3 |
| **Total (6 processes)** | **190** (the bench counts differently and says 138) |

- The Rust side is small. About three quarters of the memory is WebView2's browser and renderer processes, and the renderer's size follows
  the number of pages it holds: the bar, the menu, the submenu and the prebaked panel (ADR 0010, ADR 0016) are always loaded.
- Dropping the prebaked windows (creating the submenu and the panel on first use) is the only change that would save a lot, and it costs
  latency on the first open of each. That is a product decision (Liam), not a tuning one, so nothing was changed in v0.10.
- Smaller candidates, unmeasured: the icon data URLs held in the registry (bounded at 256 for the tray), and the WebView2 flags (ADR 0033).
