| item.update (label) until it is in the registry (median / worst of 30) | 0.4 / 0.7 ms | < 100 ms | ok |
| item.setMenu until it is in the registry (median / worst of 30) | 0.4 / 0.6 ms | < 100 ms | ok |

| Click to menu window visible (median / worst of 10) | 51.6 / 71.0 ms | < 50 ms | over |
| Memory, private (bar + WebView2) | 93 MB | < 120 MB | ok |
| Memory, working set sum (reference) | 421 MB | counts shared pages | ok |
| Memory growth over 8 h | not measured | < 5 MB | |

- 8 processes counted (the bar and its WebView2 children), 12 logical cores.
- CPU: total over 67 s after 10 s of settling, divided by cores. The ticking row is the same with `examples/test-client` running (one label update per second).
- Latency is measured over the pipe with a minimal client: the time from sending the message until `debug.listItems` shows it. The UI sees it about one frame (16 ms) later, because `items-changed` is coalesced; the render time is the UI's.
- Popovers: from the click (sent over the pipe as `debug.click`) until the app receives `popover.show` / `popover.hide`. Window visible and focused is timed with a real mouse click by `scripts/popover-latency.ps1`.
- Menus: the window time is from the click (sent over the pipe as `debug.click`) until Windows reports the menu window visible; React drawing the entries comes on top once the UI exists.
- Machine: AMD Ryzen 5 7430U with Radeon Graphics, 15 GB RAM.

## Popover window, with a real mouse click

`scripts/popover-latency.ps1` clicks the icon with real mouse input and times it until the app's window
is visible and is the foreground window (10 rounds per run, `examples/quick-note` under
Electron 45, one 3840x2160 monitor at 150%):

| What | Result | Budget | |
|---|---|---|---|
| Click to popover window visible (median / worst of 30, 3 runs) | 25 / 145 ms | < 50 ms | ok, one outlier |
| Click to popover window has keyboard focus (median / worst of 30, 3 runs) | 26 / 156 ms | < 50 ms | ok, one outlier |

- After the code-review fixes, on a fresh release build: 29 of 30 rounds were 17 to 31 ms. The one slow round (145 ms) was the first
  round of the first run, right after the app started. An earlier run on the build before the fixes: 33 / 48 ms (10 rounds).

- It is the whole path: the UI handling the click, `itemClicked`, the placement, the pipe, the app moving, showing and
  focusing its window. The poll loop adds a few ms of its own granularity.
- A click faked over the pipe (`debug.click`) shows the window but cannot give it focus: Windows only lets the bar grant
  focus after real input, so the focus numbers need the real click.
- Measured on ONE monitor at ONE scale (150%). Other monitors and scales are covered by placement unit tests
  (100, 125, 150, 200 % and negative monitor coordinates), not by a run on that hardware.

## Notes on the other rows

- **Click to menu window visible** was 17.8 / 19.8 ms in `0.3.md` and is 52 / 71 ms here. A build of `main` (before any
  v0.4 code) measured 64 / 81 ms on the same machine and the same day, so it is not caused by this release. The
  difference to `0.3.md` is probably the UI that arrived since (the menu window waits for React to report its size) and
  system load. Not investigated further.
- The menu probe (`scripts/menu-visible.ps1`) had to change: the menu and its submenu windows share a title, and
  `FindWindow` can return the hidden submenu one (the probe then timed out at 2000 ms). It now checks every window with that title.
- **Memory, private** is 93 MB, 19 MB above `0.3.md` (74 MB), still under the 120 MB budget. Not re-measured on a
  `main` build, so it is not known how much comes from the UI changes since v0.3 and how much from this release (the
  Rust additions are a few small structs). Watch it (see the menu-window memory note).
