# Performance 0.3

Measured 2026-11-10 with `pnpm bench 0.3` (release build, nothing else started).

| What | Result | Budget | |
|---|---|---|---|
| Idle CPU (avg) | 0.10% | < 0.5% | ok |
| CPU with one item updating every second | 0.02% | < 0.5% | ok |
| Connect + hello to welcome | 2.4 ms | < 100 ms | ok |
| item.create until it is in the registry (median / worst of 30) | 0.2 / 0.9 ms | < 100 ms | ok |
| item.update (label) until it is in the registry (median / worst of 30) | 0.3 / 0.6 ms | < 100 ms | ok |
| item.setMenu until it is in the registry (median / worst of 30) | 0.2 / 0.5 ms | < 100 ms | ok |
| Menu pick until the app gets menu.click (median / worst of 30) | 0.2 / 0.6 ms | < 20 ms | ok |
| Click to menu window visible (median / worst of 10) | 19.2 / 23.9 ms | < 50 ms | ok |
| Memory, private (bar + WebView2) | 78 MB | < 120 MB | ok |
| Memory, working set sum (reference) | 374 MB | counts shared pages | ok |
| Memory growth over 8 h | not measured | < 5 MB | |
| Click to popover.show | from v0.4 | < 20 ms | |

- 7 processes counted (the bar and its WebView2 children), 12 logical cores.
- CPU: total over 69 s after 10 s of settling, divided by cores. The ticking row is the same with `examples/test-client` running (one label update per second).
- Latency is measured over the pipe with a minimal client: the time from sending the message until `debug.listItems` shows it. The UI sees it about one frame (16 ms) later, because `items-changed` is coalesced; the render time is the UI's.
- Menus: the window time is from the click (sent over the pipe as `debug.click`) until Windows reports the menu window visible; React drawing the entries comes on top once the UI exists.
- Machine: AMD Ryzen 5 7430U with Radeon Graphics, 15 GB RAM.
