- 6 processes counted (the bar and its WebView2 children), 12 logical cores.
- CPU: total over 66 s after 10 s of settling, divided by cores. The ticking row is the same with `examples/test-client` running (one label update per second).
- Latency is measured over the pipe with a minimal client: the time from sending the message until `debug.listItems` shows it. The UI sees it about one frame (16 ms) later, because `items-changed` is coalesced; the render time is the UI's.

## Script items (v0.9)

- **Five script items at 10 s** are five trusted node scripts in a temp folder (`BARISTA_SCRIPTS_DIR`, trust written for their file hashes before the bar starts, so "no scripts" is the idle row). The row counts the bar and its WebView2 processes only: the scripts' own short-lived processes are gone before the second snapshot, so their cost is below.
- **Found by this bench and fixed:** the first run of the five-script row showed 1.06% (budget 0.5%). Per process, `barista.exe` itself spent about 0.2 s of CPU per script run. The cause was the thread snapshot used to find a new process's main thread (80 ms each, timed). It now uses `NtResumeProcess` on the process handle: the bar's cost with five scripts went from 0.82% to 0.06% of the machine (30 s samples), and the bench row to 0.07%.
- Memory with five scripts is not larger than without (109 MB against 131 MB in this run: the difference is WebView2 run-to-run noise, not the scripts).
- Rows marked over (menu window 51 ms, memory about 130 MB, tray icons not measured) are unchanged from v0.8 and not caused by this release.

### Cost of one script run (median of 4, process CPU time and wall time, scripts' own processes)

| Script | Wall | CPU | Sensible interval |
|---|---|---|---|
| `clock.10s.mjs` (node) | 169 ms | 125 ms | 2 s and up |
| `hello.30s.py` (py launcher) | 151 ms | 31 ms | 2 s and up |
| `system-monitor.5s.ps1` (Windows PowerShell 5.1) | 1 763 ms | 1 547 ms | 5 s and up |

- Five node scripts at 10 s: about 5 x 0.125 s per 10 s, roughly 0.5% of the 12-core machine. Five PowerShell scripts at 10 s: about 5 x 1.5 s per 10 s, roughly 6% of one core, so use `.py` or `.mjs` for anything that runs often (the v0.8 first-party system monitor is the cheap version of the showcase).
- PowerShell timings that shaped the example: `Get-CimInstance Win32_Processor` 1.1 s, `Get-Counter` 2.4 s, `Get-PSDrive` 0.18 s, `Get-Process` 0.2 s, a `try/catch` around `TotalProcessorTime` per process 3 s. The example uses `.CPU`, .NET `ComputerInfo` and `DriveInfo` (1.7 s in total, down from 4.8 s).
- No extra Barista process: the runner is inside the bar. Only the scripts' own short-lived children appear.

### Checked live on the real UI (dev bar driven over CDP, real clicks)

- Trust panel (Allow cycles "1 of 3"), live labels, colors, submenu, `href`, `shell`, `refresh`, error marks, "Disable", "Run scripts" off and on, "Open scripts folder", bar restart (no prompt for trusted scripts), edit asks again, rename `clock.10s.mjs` to `clock.1s.mjs` changes the timer with no restart, delete removes the item.
- Sleeping forever, 10 MB of output, exit 1, binary output and a script with a grandchild: each shows the error state and leaves no process behind.
