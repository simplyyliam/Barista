# Performance 0.7

Measured 2026-11-16 with `pnpm bench 0.7` (release build, nothing else started).

| What | Result | Budget | |
|---|---|---|---|
| Idle CPU (avg) | 0.07% | < 0.5% | ok |
| CPU with one item updating every second | 0.03% | < 0.5% | ok |
| Connect + hello to welcome | 3.9 ms | < 100 ms | ok |
| item.create until it is in the registry (median / worst of 30) | 0.4 / 1.7 ms | < 100 ms | ok |
| item.update (label) until it is in the registry (median / worst of 30) | 0.4 / 0.9 ms | < 100 ms | ok |
| item.setMenu until it is in the registry (median / worst of 30) | 0.4 / 0.6 ms | < 100 ms | ok |
| Menu pick until the app gets menu.click (median / worst of 30) | 0.2 / 0.4 ms | < 20 ms | ok |
| Click to popover.show reaching the app (median / worst of 30) | 1.8 / 2.7 ms | < 20 ms | ok |
| Click on the open icon to popover.hide reaching the app (median / worst of 30) | 0.3 / 0.6 ms | < 20 ms | ok |
| Click to menu window visible (median / worst of 10) | 45.6 / 56.7 ms | < 50 ms | over |
| CPU with 15 tray icons (one tooltip changing every 2 s) | 0.13% | < 0.5% | ok |
| Tray tooltip change until it is in the registry (median / worst of 12) | 19 / 1804 ms | < 1000 ms | over |
| A killed tray app's icons gone from the registry | 271 ms | < 1000 ms | ok |
| Memory, private with 15 tray icons | 122 MB | < 120 MB | over |
| Memory, private (bar + WebView2) | 145 MB | < 120 MB | over |
| Memory, working set sum (reference) | 525 MB | counts shared pages | ok |
| Memory growth over 8 h | not measured | < 5 MB | |

- 8 processes counted (the bar and its WebView2 children), 12 logical cores.
- CPU: total over 74 s after 10 s of settling, divided by cores. The ticking row is the same with `examples/test-client` running (one label update per second).
- Latency is measured over the pipe with a minimal client: the time from sending the message until `debug.listItems` shows it. The UI sees it about one frame (16 ms) later, because `items-changed` is coalesced; the render time is the UI's.
- Popovers: from the click (sent over the pipe as `debug.click`) until the app receives `popover.show` / `popover.hide`. Window visible and focused is timed with a real mouse click by `scripts/popover-latency.ps1`.
- Menus: the window time is from the click (sent over the pipe as `debug.click`) until Windows reports the menu window visible; React drawing the entries comes on top once the UI exists.
- Machine: AMD Ryzen 5 7430U with Radeon Graphics, 15 GB RAM.

## Notes (v0.7)

- v0.7 adds no polling and no timers: a tray click is a few `PostMessage` calls; the layout work runs only when an item, a pin, an order or a reported width changes.
- **Tooltip change, worst of 12: 1804 ms (v0.6: 630 ms), median 19 ms.** One slow sample out of 12 with real tray apps changing at the same time; the bench ran while the code review and the security review were running on this machine. Not re-run. If it shows again on a quiet machine it is worth a look.
- **Memory** 145 MB private (v0.6: 148 MB); the 15-icon row read 122 MB this time. Over the 120 MB budget as before; the memory pass is a v0.10 item.
- **Menu window visible** 45.6 ms median, back under the 50 ms budget (v0.6: 68.5 ms; WebView2 drift, nothing changed in menus).
- **Click latency** (command to the app's callback) was not added to `pnpm bench`: `scripts/tray-probe.ps1 -Log` logs the receive time, and a click arrives within the same millisecond as the debug click (see the log in ADR 0027's check: all messages of a click 0 to 2 ms apart).
- **Not measured:** Windows 10, memory growth over time.
