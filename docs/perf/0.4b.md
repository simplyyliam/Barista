| Memory, private (bar + WebView2) | 108 MB | < 120 MB | ok |

| Memory growth over 8 h | not measured | < 5 MB | |

- 8 processes counted (the bar and its WebView2 children), 12 logical cores.
- CPU: total over 36 s after 10 s of settling, divided by cores. The ticking row is the same with `examples/test-client` running (one label update per second).
- Latency is measured over the pipe with a minimal client: the time from sending the message until `debug.listItems` shows it. The UI sees it about one frame (16 ms) later, because `items-changed` is coalesced; the render time is the UI's.
- Popovers: from the click (sent over the pipe as `debug.click`) until the app receives `popover.show` / `popover.hide`. Window visible and focused is timed with a real mouse click by `scripts/popover-latency.ps1`.
- Menus: the window time is from the click (sent over the pipe as `debug.click`) until Windows reports the menu window visible; React drawing the entries comes on top once the UI exists.
- Machine: AMD Ryzen 5 7430U with Radeon Graphics, 15 GB RAM.

## Same-machine check against v0.4.0 (2026-11-12, slice A)

v0.4.0 was rebuilt in a worktree and benched the same day with the same scripts (`BENCH_SECONDS=30`, release builds):

| Build | Idle CPU | Click to menu window visible (median / worst) | Memory, private | Memory, working set |
|---|---|---|---|---|
| v0.4.0 rebuilt today | 0.01% | 54.0 / 72.8 ms | 101 MB | 418 MB |
| v0.4b slice A | 0.07% | 53.0 / 59.3 ms | 108 MB | 433 MB |

- The panel window (created at startup, hidden) costs about **7 MB private** and 15 MB working set. The processes count is
  unchanged (8): the panel shares the one renderer (`--renderer-process-limit=1`). Inside the 120 MB budget.
- Idle CPU went from 0.01 to 0.07%: all under the 0.5% budget; the system services sleep in `recv()` /
  `changed().await` and the audio thread has no timer. Single 30 s samples are noisy, so this is probably not real.
  Not repeated.
- **Panel open latency** (`scripts/panel-latency.ps1`, release bar, `openPanel` over the pipe until Windows reports the
  window visible, 12 rounds per run). The UI is not wired, so the window is shown by the no-UI fallback timer, which
  is the worst case (with `panelResized` it shows as soon as the UI has measured).
  Timing logs showed the Rust side is small: placement about 3 ms, `show` + `set_focus` under 1 ms; the rest was the
  fallback timer (30 ms asked, 41 ms real, because Windows timers tick in about 15 ms steps).

  | Fallback | Monitor / scale | Median (3 runs) | Worst |
  |---|---|---|---|
  | 30 ms | external, 1.5x | 56.3 / 55.0 ms | 70.8 ms |
  | 20 ms (kept) | external, 1.5x | 43.1 / 40.2 / 41.5 ms | 51.3 ms |
  | 20 ms (kept) | laptop panel, 2x | 40.9 / 40.4 / 41.0 ms | 93.8 ms (first round after moving the bar) |

  Inside the 50 ms budget at the median on both monitors and scales. Re-measure when the UI is in.
- **Placement** was checked on both monitors (laptop panel left of the primary at 2x with negative x, external 3840x2160 at
  1.5x), with the item near the left edge, in the middle and near the right edge: top on the bar's bottom, left on
  the item, shifted left at the right edge with the 10 px margin, always inside the monitor.

## With the real UI wired (2026-11-12)

After a minimal panel widget was added (it reports its size with `panelResized` and closes on Esc), on the laptop panel
(the only monitor at that moment), release build, `scripts/panel-latency.ps1`, 12 rounds x 3 runs:

| Run | Median | Worst |
|---|---|---|
| 1 | 38.8 ms | 43.0 ms |
| 2 | 39.7 ms | 44.7 ms |
| 3 | 39.8 ms | 50.2 ms |

- A real Escape key closed the panel through the UI's own listener (no injected code); the window was sized to the UI's
  measurement (290x142 px) instead of the first guess.
- The numbers did not drop below the fallback case. Most likely the hidden page renders its first frame about as late as
  the 20 ms fallback fires, so both paths land near 40 ms. Not investigated further; inside the 50 ms budget.

## Notifications reader (slice C, 2026-11-12)

Debug build, 12 s idle windows, `Get-Process barista` CPU seconds:

| State | Idle CPU over 12 s |
|---|---|
| `windows` mode (reader off) | 0.00 s |
| Reader on, first version (refresh on every folder write) | 0.28 s per 10 s (about 3%) |
| Reader on, with the toast fingerprint | 0.00 s |

- The first version looped: reading through `UserNotificationListener` writes to Windows' notification database (the WAL grew about 1 MB per read), which woke the folder watcher, which read again. The fingerprint (ids and arrival times, read-only) stops that. ADR 0018.
- With the fix the database's WAL file is quiet at idle too (checked by file time).
- Memory and the release-build `pnpm bench` were not re-run for this slice.
