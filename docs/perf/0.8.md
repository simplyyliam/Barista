- 8 processes counted (the bar and its WebView2 children), 12 logical cores.

## First-party items (2026-11-16, release bar, 12 logical cores, working set and private bytes)

Measured by starting the release bar, then each client, waiting 45 s and sampling 30 s (`private` is committed memory,
`working` is what is resident). The clients are separate apps, not part of the bar (ADR 0030), so they are listed apart.

| Client | Processes | Private | Working set | CPU |
|---|---|---|---|---|
| Bar (8 processes) with the three clients connected | 8 | 219 MB | 527 MB | 0.18% |
| Mic mute (Node + win-helper) | 3 | 130 MB | 121 MB | 0% |
| Now playing (Node + win-helper) | 3 | 130 MB | 126 MB | 0% |
| System monitor (Electron: main, GPU, renderer, utility) | 4 | 321 MB | 441 MB | 0.02% |

- **Found by measuring:** importing icons from the `@hugeicons/core-free-icons` index loads thousands of icon modules. Mic mute
  and now playing took 187 MB private; importing only the icon files they use (`@hugeicons/core-free-icons/Mic01Icon`) saved
  about 58 MB each. All three apps now do that.
- The helper itself is small (about 11 MB working set each). The rest of a Node client is Node and the SDK.
- The system monitor is an Electron app on purpose (it is a client like any other, ADR 0030): about 440 MB working set while
  idle. Its CPU is 0.02% (one sample and one label update per second). If that memory is not acceptable for people who keep
  it running, the escape hatch in the release file is to sample in Rust and let the bar draw the numbers.
- The bar's own private memory is 162 MB right after the start (table above) and 219 MB after a minute with three clients
  connected and the panels warmed. Budget is 120 MB; v0.4b already accepted 130 MB and v0.7 measured 145 MB. This is the
  number to watch in the 8 hour run: **the 8 hour soak with the system monitor on was not run in this session** (`scripts/soak.ps1`,
  Liam), so "bench in budget after 8 hours" is open.
- Tray icons were "not measured" by the bench this time: the fake tray icon script did not show icons. Not investigated.
- Menu click to window visible: median 48 ms (budget 50), worst 122 ms in one run; v0.7 sat at 42 to 46 ms.

## Where the memory is (2026-11-18, throwaway build that could skip hidden windows, not committed)

The bar starts four webview windows, each loading the whole app: the bar, the menu, the submenu and the panel. They share one
renderer. Bar alone, private working set after a 40 s settle:

| Config | Bar alone |
|---|---|
| Normal | 141 MB |
| Without the panel window | 88 MB (**the panel window costs about 53 MB**) |
| Without the submenu window | 133 MB (about 8 MB) |
| Without both | 92 MB |

- The panel window is the one to fix: it is warmed up at startup with the notifications page painted (`panel.rs` `warm_up`), and it
  keeps what it last showed in the DOM. The menu window is cheap in comparison.
- Ideas, in the order I would try them: (1) the panel's React tree renders nothing while the panel is closed (the window stays
  warm, so the first show stays instant); (2) warm it with a light page instead of the notifications; (3) create it on first use
  (first open slower, and users open the clock or Wi-Fi panel all day, so this one saves little).
- (1) and (2) are in `apps/bar/src/features/panel` and `widgets/panel`, the user's frontend. Not done.

- **Settle time matters:** the same committed build read 178 to 181 MB (40 s after the first start following a rebuild) and then
  133 to 135 MB (60 s settle). Samples taken early after a start, or right after a build, are too high. Use `-Settle 60` or more
  in `scripts/settings-memory.ps1`, and compare runs with the same settle time.

## Panel memory ideas, tried (2026-11-18)

- **Unmount the panel's routes after 20 s closed:** 137 MB, no gain. Unmounting React does not give memory back to the OS; the
  53 MB is the cost of the fourth page itself, not of what it shows. Reverted.
- **One chunk per window (`App.tsx`, lazy widgets):** each window now loads only its own widget. Bar alone 132.5 MB at a 60 s
  settle (was 133 to 137), `pnpm bench` 140 MB (was 143 to 144), settings window open 160 MB, menu click to window visible
  47.4 / 49.9 ms (budget 50). Control center panel opens fully loaded (checked with `PrintWindow` on the panel window).
  Kept: small gain, nothing slower.
- **What is left:** every WebView2 page costs a base of roughly 25 to 50 MB (a V8 context, the DOM, React). The bar has four of
  them hidden or visible (bar, menu, submenu, panel). Real savings now need fewer windows: one window for the menu and the submenu,
  or the panel and the menus sharing a window. That is a new ADR and a release of its own (the v0.10 speed and memory pass).
- Plain screen capture does not show the menu and panel windows (acrylic, no activate); use `PrintWindow` with flag 2, and the
  display is 3840 wide at 150%, so make the capture script DPI aware.

- **Not the bundle size:** after the split the biggest JS chunks are panel 330 KB, shared 245 KB, settings 205 KB (CSS 91 KB, Inter
  fonts about 200 KB). A page's cost is its base (document, compositor, V8 context), so only fewer pages save real memory.
