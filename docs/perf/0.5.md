# Performance 0.5

Measured 2026-11-14 with `pnpm bench 0.5` (release build, nothing else started).

| What | Result | Budget | |
|---|---|---|---|
| Idle CPU (avg) | 0.05% | < 0.5% | ok |
| CPU with one item updating every second | 0.03% | < 0.5% | ok |
| Connect + hello to welcome | 2.5 ms | < 100 ms | ok |
| item.create until it is in the registry (median / worst of 30) | 0.3 / 1.0 ms | < 100 ms | ok |
| item.update (label) until it is in the registry (median / worst of 30) | 0.3 / 0.5 ms | < 100 ms | ok |
| item.setMenu until it is in the registry (median / worst of 30) | 0.3 / 0.5 ms | < 100 ms | ok |
| Menu pick until the app gets menu.click (median / worst of 30) | 0.2 / 0.6 ms | < 20 ms | ok |
| Click to popover.show reaching the app (median / worst of 30) | 0.9 / 1.4 ms | < 20 ms | ok |
| Click on the open icon to popover.hide reaching the app (median / worst of 30) | 0.2 / 2.4 ms | < 20 ms | ok |
| Click to menu window visible (median / worst of 10) | 48.9 / 81.1 ms | < 50 ms | over |
| Memory, private (bar + WebView2) | 150 MB | < 120 MB | over |
| Memory, working set sum (reference) | 510 MB | counts shared pages | ok |
| Memory growth over 8 h | not measured | < 5 MB | |

- 8 processes counted (the bar and its WebView2 children), 12 logical cores.
- CPU: total over 64 s after 10 s of settling, divided by cores. The ticking row is the same with `examples/test-client` running (one label update per second).
- Latency is measured over the pipe with a minimal client: the time from sending the message until `debug.listItems` shows it. The UI sees it about one frame (16 ms) later, because `items-changed` is coalesced; the render time is the UI's.
- Popovers: from the click (sent over the pipe as `debug.click`) until the app receives `popover.show` / `popover.hide`. Window visible and focused is timed with a real mouse click by `scripts/popover-latency.ps1`.
- Menus: the window time is from the click (sent over the pipe as `debug.click`) until Windows reports the menu window visible; React drawing the entries comes on top once the UI exists.
- Machine: AMD Ryzen 5 7430U with Radeon Graphics, 15 GB RAM.

## Memory: same as v0.4.1 on the same day

Private memory reads 150 MB here, over the 120 MB budget (130 MB was accepted in v0.4b). The v0.5 changes add a few
tasks and timers per client, so it was compared against the installed v0.4.1 build, started the same way (20 s settle,
3 samples, A B A B order):

| Build | Private memory (MB, 3 samples each) |
|---|---|
| v0.4.1 (installed) | 161 / 161 / 153 and 162 / 162 / 152 |
| v0.5 branch | 164 / 164 / 155 and 160 / 160 / 151 |

Same numbers: the growth is WebView2 and the UI since v0.4b, not this release. Menu latency over 50 ms is the known
WebView2 drift (see `0.4.md`).

## Never stuck (`pnpm lifecycle`, release build, 12 logical cores)

| What | Result | Budget | |
|---|---|---|---|
| Kill the client: its item is gone (median / worst of 20) | 47 ms / 48-77 ms (3 runs), 0 dead icons, 0 left at the end | 0 dead icons | ok |
| Client that never pongs: its item is removed | 15.0 s | 15 to 20 s | ok |
| Restart the bar: all 3 clients' items are back (median / worst of 5), counted from the pipe answering | 435 / 486 ms (retry cap 0.5 s; with the earlier 1 s cap: 361 / 900, 545 / 1015, 454 / 988 ms) | < 2000 ms | ok |
| Same restart, counted from launching `barista.exe` (its own startup included) | 1245 / 1278 ms (retry cap 0.5 s; with the 1 s cap: median 1.1 to 1.2 s, worst 1.9 to 2.0 s) | < 2000 ms | ok |
| Client started before the bar: its item appears | 140 to 577 ms (three runs) | < 2000 ms | ok |
| Bar quits politely (`quit_bar`): the client hears `shutdown { quit }` before the pipe closes | heard it | `shutdown:quit` | ok |

- The first restart row starts its clock when the bar answers on its pipe: that is the SDK's share (it retries every half second
  at most, so the worst case is about half a second plus one connection). The second row counts from launching the bar. Before
  the pipe was opened at the start of setup (`lib.rs`: `ipc::start` right after the registry exists) that was about 2.2 s,
  because the pipe only opened after the window, panel and system services (about 1.7 s). Now the pipe is up early and the
  median is 1.2 s. An item that arrives before the UI is mounted is still drawn (checked: client first, bar second, the item
  was in the bar's page about 1.5 s after the bar started).
- `scripts/lifecycle-client.mjs` is the client (the test client needs about 10 s to load its icons, which would hide
  the timings). The script keeps one connection to read items so polling does not make the pipe busy for the clients.
