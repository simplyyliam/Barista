- 8 processes counted (the bar and its WebView2 children), 12 logical cores.
- CPU: total over 69 s after 10 s of settling, divided by cores. The ticking row is the same with `examples/test-client` running (one label update per second).
- Latency is measured over the pipe with a minimal client: the time from sending the message until `debug.listItems` shows it. The UI sees it about one frame (16 ms) later, because `items-changed` is coalesced; the render time is the UI's.
- Popovers: from the click (sent over the pipe as `debug.click`) until the app receives `popover.show` / `popover.hide`. Window visible and focused is timed with a real mouse click by `scripts/popover-latency.ps1`.
- Menus: the window time is from the click (sent over the pipe as `debug.click`) until Windows reports the menu window visible; React drawing the entries comes on top once the UI exists.
- Machine: AMD Ryzen 5 7430U with Radeon Graphics, 15 GB RAM.

## Tray notes (v0.6)

- **Tray rows** use `scripts/tray-icons.ps1`: 15 fake icons, one tooltip and one picture changing every 2 s, running next to the real tray apps on this machine (about 11 icons, some changing every second). The tooltip row compares the moment the fake app sent a change (its own clock) with the moment `debug.listItems` showed it, polled every 20 ms. The cleanup row kills the app with `taskkill /F`, so its window dies without a clean shutdown.
- **A first run read 0.99 % idle CPU and 1.9 s worst tooltip latency.** That run was disturbed: the bar was being used (hovering, a monitor switch) and Explorer was restarted during it. A quiet 30 s sample of the same build split by process showed 0.08 % for the whole tree, `barista.exe` itself 0.017 %. Run the bench with nobody touching the bar.
- **Memory** is 148 MB, the same as v0.5 (150 MB); 15 more tray icons add about 9 MB. Still over the 120 MB budget; the memory pass is a v0.10 item.
- **Menu window visible** read 68.5 ms here (v0.5: 48.9). Menus did not change in v0.6; WebView2 start-up drift and machine load, see `docs/perf/0.4.md`. Not investigated.
- **Keeping the top place** (`scripts/tray-zorder.ps1`, Windows 11 build 26300, 3 rounds per trigger): Win+D, Win+B, Win+T and Alt+Tab never put Explorer's window above ours; while the Start menu is open Explorer is first the whole time and we are back on top once it closes. A 100 ms retry timer did not change that, so there is none. Details in ADR 0026.
- **Not measured:** Windows 10 (only Windows 11 here), memory growth over time, 15 icons on a battery.
